# Project Context

อัปเดตล่าสุด: 2026-11-19

## ภาพรวม

ระบบ Cash Flow ภายในบริษัท สำหรับติดตามและบริหารข้อมูลกระแสเงินสด โดยจะพัฒนาและปรับรายละเอียดตาม workflow จริงของบริษัททีละส่วน

## ความต้องการที่ยืนยันแล้ว

- ระบบต้องรันบน server ด้วย Docker
- ระบบต้องมี Login
- ระบบต้องจดจำและตรวจสอบย้อนหลังได้ว่าใครเปลี่ยนข้อมูลอะไร และเปลี่ยนเมื่อไร
- โครงสร้างระบบต้องรองรับการเพิ่มรายละเอียดและฟีเจอร์ย่อยในอนาคต
- ระบบต้องรองรับทั้งกระแสเงินสดที่เกิดขึ้นจริง (Actual) และประมาณการล่วงหน้า (Forecast)
- ระบบจะมีรายละเอียดเกี่ยวกับเครดิตหลายส่วน โดยจะเก็บ requirement และเพิ่มเข้าระบบทีละส่วน
- ระหว่างพัฒนาต้องเปิดทดลองได้เร็วหลังแก้โค้ด โดยไม่ต้อง rebuild ทุกครั้ง
- ใช้การพัฒนาแบบตัวต้นแบบ: สร้างระบบที่กดทดลองได้ก่อน แล้วปรับ requirement และ workflow จาก feedback ทีละรอบ
- มีบทบาท Admin ซึ่งทำได้ทุกอย่าง รวมถึงสร้างบทบาท กำหนดสิทธิ์ และสร้างบัญชีผู้ใช้
- UI ต้องเป็นชิ้นส่วนแยกจาก authentication และ business logic เพื่อให้เปลี่ยนหน้าตาหรือเพิ่ม UI แบบอื่นได้โดยใช้ logic และฐานข้อมูลเดิม
- Business Admin จัดการผู้ใช้ บทบาท สิทธิ์ และรหัสผ่านเริ่มต้นผ่าน UI หลักของ Cash Flow โดยไม่เข้าถึง Django System Admin
- Developer/Superuser ใช้ Django System Admin เพื่อดูแลโครงระบบ ข้อมูลภายใน และ Audit Event โดยลิงก์ Developer console แสดงเฉพาะบัญชี Developer/Superuser
- หน้า Cash Flow รุ่นแรกต้องแสดงเป็นตารางที่มีวันที่ รายการ เงินเข้า เงินออก และเงินคงเหลือ โดยเริ่มจากข้อมูลจำลองเพื่อปรับหน้าจอก่อนกำหนด schema ข้อมูลจริง

## ปัญหาหลักของบริษัท (ยืนยัน 2026-11-08)

- มีคนแก้ไขรายการต่าง ๆ โดยระบุไม่ได้ว่าใครแก้ แก้เมื่อไร และแก้อะไร จึงต้องมีระบบ Login และไทม์ไลน์ประวัติการแก้ไขของทุกรายการ
- บริษัทมีระบบ PO เดิมอยู่แล้ว (มีขั้นอนุมัติ ใบขอซื้อ PR และสถานะเชื่อมโปรแกรมบัญชี Bplus) ยังไม่ได้ตัดสินใจว่าจะใช้ระบบใหม่แทนหรือดึงข้อมูลจากระบบเดิม

## ทะเบียนใบสั่งซื้อ (PO)

ผู้ใช้ให้ทำหน้ากรอก PO บนเว็บก่อน โดยใช้ช่องเท่าที่มีในรายงาน "รายการใบสั่งซื้อ PO" ของระบบเดิม

### ยืนยันแล้ว

- ช่องข้อมูลตามรายงานระบบเดิม: หมายเลข PO, รหัสและชื่อผู้ขาย, ยอดรวม, วันเวลาทำรายการ, วันที่จัดส่ง, สถานะ, สถานะอนุมัติ
- ทุกการบันทึก แก้ไข และยกเลิกต้องมีชื่อผู้ทำและเวลา และแสดงเป็นไทม์ไลน์
- PO ต้องแสดงในหน้า Cash Flow เป็นเงินออกที่คาดว่าจะจ่าย
- ภาษีใน PO มี VAT 7% และหัก ณ ที่จ่าย (ยอดรวมในรายงานระบบเดิมรวม VAT แล้ว แต่ยังไม่หัก ณ ที่จ่าย)

### ข้อสังเกตจากรายงานตัวอย่างของระบบเดิม

- ยอดรวมทุกใบเท่ากับยอดก่อน VAT × 1.07 และเก็บทศนิยม 3 ตำแหน่ง
- เลขที่รูปแบบ `PO<ปี พ.ศ. 2 หลัก><เดือน>/<ลำดับ>` เช่น PO6911/028 ใบที่รออนุมัติใช้เลข PR เช่น PR6911/038
- รหัสผู้ขายรูปแบบ `<ตัวอักษร>-<ตัวเลข>` เช่น บ-006
- ระบบเดิมมีตัวกรองสถานะ Bplus และสถานะยืนยัน แต่รายงานไม่แสดงค่าของสองช่องนี้

### สมมติฐานที่ใช้ในตัวต้นแบบ (รอยืนยัน)

- กรอกหมายเลข PO เองตามระบบเดิม ระบบไม่ออกเลขให้ เมื่อ PR ได้รับอนุมัติให้แก้เลขเป็น PO และประวัติจะเก็บเลขเดิมไว้
- ปัดยอดรวมเป็นสตางค์แบบครึ่งขึ้น
- วันครบกำหนดจ่าย = วันที่จัดส่ง + เครดิตเทอมของผู้ขาย และกำหนดเองได้
- สถานะที่รู้แน่มีแค่ "ใบสั่งซื้อใหม่" สถานะอื่น (รับของแล้ว, ปิดแล้ว, ยกเลิก) ตั้งขึ้นเองรอรายงานแบบทุกสถานะ
- สถานะอนุมัติเป็นเพียงข้อมูลที่บันทึกตามระบบเดิม ระบบใหม่ยังไม่มีขั้นอนุมัติเอง
- แก้ไขได้ทุกช่องจนกว่าจะยกเลิก โดยไม่บังคับใส่เหตุผลการแก้ไข การยกเลิกต้องมีเหตุผล และไม่มีการลบ
- เงินออกที่คาดว่าจะจ่ายนับเฉพาะ PO ที่อนุมัติแล้วและสถานะใบสั่งซื้อใหม่หรือรับของแล้ว ใช้ยอดรวม VAT ซึ่งสูงกว่ายอดจ่ายจริงเท่ากับหัก ณ ที่จ่าย

## ข้อมูลผู้ขายและเครดิต (ยืนยัน 2026-11-09)

ได้ไฟล์ "ข้อมูลเครดิตของ Supplier" จากระบบเดิม มี 3 ชีต: "รายการ ผู้ผลิต" (ผู้ขายของระบบจัดซื้อ พร้อมรายละเอียดและประเภท), "เครดิต" (เจ้าหนี้ทั้งหมดพร้อมกลุ่มเจ้าหนี้) และ "รายการ ราคาสินค้าจากผู้ผลิต" (ยังไม่ได้ใช้)

- เครดิตอ่านจากชื่อกลุ่มเจ้าหนี้: "เครดิต N วัน" และ "ภายใน N วัน" = เครดิต N วันนับจากวันส่งของ (ผู้ใช้ยืนยัน), "เจ้าหนี้เงินสด" = 0 วัน
- กลุ่มที่ไม่มีจำนวนวัน (เช่น "เจ้าหนี้อื่น", "เจ้าหนี้การค้า-ในประเทศ") ให้ติดป้ายเครดิตไม่ระบุ และให้ฝ่ายบัญชีกรอกเอง (ผู้ใช้ยืนยัน)
- ผู้ขายที่มีหมายเหตุ "ยกเลิกซื้อขาย" ถือว่าเลิกใช้งาน
- ระหว่างที่ยังไม่ระบุเครดิต ระบบนับวันครบกำหนดจ่ายเท่ากับวันที่จัดส่ง (สมมติฐาน: ประมาณการแบบระวังไว้ก่อน)

## Requirement จากการประชุม 16 พ.ย. 2569

ถอดจากไฟล์เสียงและวิดีโอการประชุม (ถอดเสียงอัตโนมัติ มีจุดที่ฟังไม่ชัด)

### ยืนยันแล้ว

- เก็บหน้าเดิมไว้ และเพิ่มหน้ารายการรายวัน: ยอดยกมา เงินเข้า เงินออกแยกประเภท เลือกช่วงวันที่ได้ ข้อมูลชุดเดียวกันดูได้สองแบบ (สรุปรายวัน / รายการต่อเนื่อง) สลับไปมาได้
- หน้าประวัติการแก้ไข (ใคร เมื่อไร แก้อะไร) และไม่ต้องให้ทุกคนเห็น
- PO มาจากเว็บเดิมผ่าน API หลัง PR อนุมัติ ถ้าไม่มี API ให้มีช่องอัปโหลดไฟล์ ข้อมูลมีวันส่งแต่ไม่มีเครดิต ระบบบวกเครดิตตามรหัสผู้ขาย
- ผู้ขายบางรายผูกกับวงเงินกู้ของธนาคาร (ธนาคารจ่ายก่อนแล้วเรียกเก็บเรา วันจ่ายยืดตามเงื่อนไขธนาคาร)
- เงินเข้าแยกเป็น เงินสด, เครดิต, เงินกู้/วงเงินธนาคาร, แลกตั๋ว/ขายบิล
- อัปโหลดไฟล์ใบขายเพื่อรู้ว่าลูกค้าแต่ละรายจะจ่ายวันไหน เท่าไหร่
- แผนรับเงินประมาณการ (เช่น BJ 25 ล้าน, แม็คโคร 5 ล้าน) แล้วผูกบิลจริงมาเทียบ ส่วนต่างคือเงินที่ขาดจากกระแสเงินสด ไม่ใช่กำไรขาดทุน
- ยอดธนาคารต้องกระทบกับระบบรายวัน มีประมาณ 5 ธนาคาร ต้องมีระบบธนาคารก่อนใช้งานจริง แต่ตอนนี้ยังไม่มีข้อมูลธนาคาร จึงให้จับกลุ่มตามลูกค้าไปก่อน
- ลำดับงาน: ทำชุดรับเงิน (รวมแม็คโคร) ก่อน แล้วค่อยอัปเดต
- อนาคต: ผู้ช่วย AI "จินนี่" ตรวจจ่ายซ้ำ/ลืมจ่าย ยอดผิดปกติ และแนะนำการเปิดบิลซื้อ

### ต้องถามยืนยัน

- เงื่อนไขแม็คโคร: ได้ 85% หลัง invoice กี่วัน ส่วนที่เหลือเมื่อไร และ 5% คืออะไร
- เงื่อนไขวงเงินแต่ละธนาคาร และผู้ขาย/ลูกค้าที่อยู่ในวงเงิน
- ใครทำ API จากเว็บเดิม และส่งช่องอะไร
- บทบาทไหนเห็นหน้าประวัติการแก้ไขได้
- รูปแบบไฟล์ยอดขายเงินสด (CS…) ที่เป็นรายงานหลายแถวต่อเอกสาร

## วิธีเก็บ Requirement

- ไม่กำหนด workflow, Budget, เครดิต และรายงานทั้งหมดล่วงหน้า เพราะรายละเอียดมีจำนวนมากและยังมองภาพจากเอกสารได้ยาก
- เริ่มจากข้อมูลและหน้าจอแบบทั่วไปด้วยข้อมูลจำลอง แล้วให้ผู้ใช้ทดลองและสั่งปรับทีละรอบ
- เรื่องที่ยังไม่ชัดเจนไม่ควรปิดทางด้วยโครงสร้างตายตัว แต่ต้องแยกส่วนให้เปลี่ยนหรือขยายได้

## แหล่งข้อมูลปัจจุบัน

- ปัจจุบันบริษัทใช้ Excel
- ไม่สามารถนำไฟล์ Excel จริงมาเปิดเผยได้ จึงต้องถอด workflow จากคำอธิบายและใช้ข้อมูลจำลองในการพัฒนาและทดสอบ

## หลักการสำคัญ

- ความถูกต้องของข้อมูลทางการเงินสำคัญกว่าความสะดวกในการแก้ไขย้อนหลัง
- การเข้าถึงและการเปลี่ยนข้อมูลต้องตรวจสอบสิทธิ์ฝั่ง server เสมอ
- Audit trail ต้องเก็บอย่างน้อย: ผู้กระทำ, เวลา, ประเภทการกระทำ, ชนิดและรหัสรายการ, ค่าเดิม และค่าใหม่เมื่อเหมาะสม
- Admin สร้างบัญชีหรือสั่ง reset รหัสผ่านได้ แต่ระบบต้องเก็บเฉพาะ password hash และห้ามแสดงรหัสผ่านเดิมของผู้ใช้
- Business Admin ต้องไม่เห็นหรือแก้ไขบัญชี Developer/Superuser
- วันเวลาในระบบควรเก็บในฐานข้อมูลเป็น UTC และแสดงผลตามเขตเวลา `Asia/Bangkok`
- จำนวนเงินต้องใช้ชนิดข้อมูล decimal/fixed precision ไม่ใช้ floating point

## เรื่องที่ยังไม่ได้กำหนด

- บทบาทอื่นนอกจาก Admin และสิทธิ์ของแต่ละบทบาท
- ขั้นตอนการเพิ่ม แก้ไข อนุมัติ และยกเลิกรายการ
- ประเภทบัญชี รายรับ รายจ่าย หมวดหมู่ และมิติข้อมูลที่บริษัทใช้งานจริง
- รูปแบบรายงาน Dashboard และการ export
- วิธี deploy, domain, HTTPS, backup และการกู้คืนข้อมูล
- การรองรับหลายบริษัท หลายสาขา หรือหลายสกุลเงิน
- ขอบเขตและวิธีจัดการ Budget (รอยืนยันว่าคำว่า “บาทเน็ต” หมายถึง Budget หรือไม่)
- ประเภทเครดิต วงจรเครดิต และผลต่อวันที่รับหรือจ่ายเงินจริง
- ระบบใหม่จะแทนระบบ PO เดิม หรือดึงข้อมูลจากระบบเดิม (นำเข้า Excel)
- ระบบใหม่ต้องมีขั้นอนุมัติ PR/PO เองหรือไม่ (ผู้ใช้ยังไม่แน่ใจ)
- รายการสถานะทั้งหมดของระบบ PO เดิม และความหมายของสถานะ Bplus กับสถานะยืนยัน
- รูปแบบไฟล์ Excel ที่ใช้ทำ cash flow ในปัจจุบัน (บริษัทยังไม่มีไฟล์ให้ดู)
- เครดิตของผู้ขาย 47 รายที่ยังไม่ระบุ (ฝ่ายบัญชีกรอก)
- การบันทึกการจ่ายเงินจริงของ PO และการเปลี่ยนจาก Forecast เป็น Actual
- บทบาทฝ่ายจัดซื้อและผู้ดูอย่างเดียว ว่าแต่ละคนควรได้สิทธิ์ PO ข้อใดบ้าง
