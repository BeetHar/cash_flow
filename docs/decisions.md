# Technical Decisions

บันทึกนี้เก็บเฉพาะการตัดสินใจที่มีผลต่อทิศทางระบบ เพื่อไม่ให้เหตุผลสูญหายเมื่อโครงการโตขึ้น

## DEC-001: ใช้ Docker สำหรับการรันระบบ

- สถานะ: ยืนยันแล้ว
- วันที่: 2026-10-05
- การตัดสินใจ: ทุก service ของระบบต้องจัดให้รันผ่าน Docker ได้
- เหตุผล: ทำให้ environment บนเครื่องพัฒนาและ server สม่ำเสมอ และช่วยให้ติดตั้งหรือย้ายระบบง่ายขึ้น
- รายละเอียดยังต้องเลือก: รูปแบบ image, reverse proxy, volume, network และขั้นตอน deploy

## DEC-002: ระบบต้องมี Authentication

- สถานะ: ยืนยันแล้ว
- วันที่: 2026-10-05
- การตัดสินใจ: ผู้ใช้ต้อง Login ก่อนเข้าถึงข้อมูลที่ได้รับการป้องกัน
- ข้อกำหนดขั้นต่ำ: เก็บรหัสผ่านด้วย password hashing ที่ปลอดภัย, มี session/token expiration และตรวจสิทธิ์ฝั่ง server
- รายละเอียดยังต้องเลือก: session หรือ token, นโยบายรหัสผ่าน, การ reset รหัสผ่าน และ MFA

## DEC-003: การเปลี่ยนข้อมูลต้องตรวจสอบย้อนหลังได้

- สถานะ: ยืนยันแล้ว
- วันที่: 2026-10-05
- การตัดสินใจ: การเปลี่ยนข้อมูลธุรกิจต้องสร้าง audit record ที่เชื่อมโยงกับผู้ใช้และเวลาที่เกิดเหตุการณ์
- ข้อควรระวัง: audit record ไม่ควรถูกแก้ไขหรือลบผ่านหน้าจอใช้งานปกติ และต้องไม่บันทึกรหัสผ่านหรือ secret

## DEC-004: ใช้ Django และ PostgreSQL เป็น Application Stack

- สถานะ: ยืนยันเบื้องต้น
- วันที่: 2026-10-05
- ภาษาและ backend: Python 3.14 กับ Django 5.2 LTS
- Database: PostgreSQL 18
- Frontend ระยะแรก: Django Templates และ HTMX โดยยังไม่แยกเป็น SPA
- เหตุผล: เป็นโครงสร้างแบบ monolith ที่ปรับหน้าจอและ business rule ได้เร็ว มี authentication, authorization, migrations และ admin interface เป็นพื้นฐาน และลดงานเชื่อมต่อหลายโปรเจกต์
- แนวทางข้อมูลการเงิน: ใช้ PostgreSQL `numeric` และ Python `Decimal` สำหรับจำนวนเงิน
- แนวทางอนาคต: แยก API หรือ frontend ภายหลังได้เมื่อมี use case ที่คุ้มกับความซับซ้อน และประเมินการอัปเกรดเป็น Django 6.2 LTS เมื่อรุ่นดังกล่าวเสถียร

## DEC-005: ใช้ Docker Compose เป็น Development Loop

- สถานะ: ยืนยันเบื้องต้น
- วันที่: 2026-10-05
- การตัดสินใจ: เตรียมคำสั่งเริ่มระบบแบบสั้น และใช้ auto reload/Compose Watch เพื่อให้การแก้ source code แสดงผลโดยไม่ rebuild image ทุกครั้ง

## DEC-006: พัฒนาแบบ Prototype-Driven และ Iterative

- สถานะ: ยืนยันแล้ว
- วันที่: 2026-10-05
- การตัดสินใจ: ไม่รอ requirement ด้าน Cash Flow, Budget, เครดิต และรายงานให้ครบก่อนเริ่ม แต่สร้างตัวต้นแบบที่ใช้งานได้จากสมมติฐานทั่วไปและข้อมูลจำลอง แล้วปรับจาก feedback ทีละรอบ
- ข้อกำหนด: สมมติฐานต้องแก้หรือขยายได้ง่าย และห้ามนำสมมติฐานที่ยังไม่ยืนยันไปทำเป็นข้อจำกัดที่เปลี่ยนยาก

## DEC-007: Admin จัดการผู้ใช้ บทบาท และสิทธิ์ได้

## DEC-008: แยก Presentation ออกจาก Business Modules

- สถานะ: ยืนยันแล้วและเริ่มใช้งาน
- วันที่: 2026-10-05
- การตัดสินใจ: หน้าเว็บอยู่ใต้ `presentation/web` ส่วนข้อมูลและ logic ของผู้ใช้อยู่ใต้ `modules/identity`

## DEC-009: แยก Business Admin ออกจาก Developer Superuser

- สถานะ: ยืนยันแล้วและเริ่มใช้งาน
- วันที่: 2026-10-06
- Business Admin: ใช้ UI หลักภายใต้ `/settings/` เพื่อสร้างและแก้ผู้ใช้ สร้างบทบาท กำหนดสิทธิ์ และ reset รหัสผ่าน
- Developer/Superuser: ใช้ `/system-admin/` เพื่อดูแลฐานข้อมูล โครงระบบ และ Audit Event โดยแสดงลิงก์ในเมนูหลักเฉพาะบัญชี Developer/Superuser
- ขอบเขต: Business Admin ไม่เป็น `is_staff` หรือ `is_superuser` มองไม่เห็นบัญชี Developer และไม่สามารถเข้าถึง Developer console
- การป้องกัน: Business Admin แก้บทบาทผู้ดูแลระบบหลักหรือเปลี่ยนบทบาทของบัญชีตัวเองไม่ได้ เพื่อลดโอกาสล็อกตัวเองออกจากระบบ

## DEC-010: Audit Trail เป็นโมดูลกลางแบบ Append-Only

- สถานะ: ยืนยันแล้วและเริ่มใช้งาน
- วันที่: 2026-10-06
- การตัดสินใจ: การเปลี่ยนผู้ใช้ บทบาท สิทธิ์ และรหัสผ่านผ่าน UI หลักสร้าง `AuditEvent`

## DEC-011: โมดูลจัดซื้อแยกเป็น `modules/procurement`

- สถานะ: ยืนยันแล้วและเริ่มใช้งาน
- วันที่: 2026-11-02
- การตัดสินใจ: ผู้ขายและใบสั่งซื้ออยู่ใน `modules/procurement` โดย UI เรียกผ่าน `services.py` เท่านั้น
- สิทธิ์: ใช้ custom permissions 3 ข้อ ได้แก่ `view_purchase_orders`, `manage_purchase_orders` และ `manage_suppliers` โดยสิทธิ์จัดการรวมสิทธิ์ดูไว้ด้วย และปิด default permissions ของ Django เพื่อให้หน้าบทบาทแสดงเฉพาะสิทธิ์ที่มีความหมายทางธุรกิจ
- Audit: ทุก service ที่เปลี่ยนข้อมูลบันทึก `AuditEvent` พร้อม snapshot ก่อน/หลัง จำนวนเงินเก็บเป็นข้อความเพื่อไม่ให้เสียความละเอียด
- Developer console: ดูข้อมูลจัดซื้อได้อย่างเดียว เพราะการแก้ข้อมูลต้องผ่าน service เพื่อให้มี audit trail

## DEC-012: กติกาคำนวณเงินของ PO

- สถานะ: พักไว้ (แทนที่ด้วย DEC-015 เมื่อ 2026-11-08) โค้ดถูกนำออกแล้ว ใช้เป็นแนวทางได้ถ้ากลับมาทำ PO แบบมีรายการสินค้า
- วันที่: 2026-11-02
- ตำแหน่ง: `modules/procurement/calculations.py` เป็นฟังก์ชันล้วนที่ทดสอบแยกได้
- กติกา: จำนวนเงินต่อบรรทัด = จำนวน × ราคาต่อหน่วย, VAT คิดจากยอดรวมก่อน VAT ทั้งใบ, หัก ณ ที่จ่ายคิดจากยอดก่อน VAT โดยรวมฐานตามอัตราก่อนแล้วปัดทีละอัตรา, ยอดจ่ายจริง = ยอดรวม VAT − หัก ณ ที่จ่าย
- การปัดเศษ: 2 ตำแหน่งแบบครึ่งขึ้น (`ROUND_HALF_UP`) ทุกจุด ไม่ใช้ banker's rounding
- การเก็บข้อมูล: เก็บยอดที่คำนวณแล้วไว้ใน PO เพื่อให้ query รายงานได้เร็ว และคำนวณใหม่ทุกครั้งที่แก้ร่าง เก็บอัตรา VAT ไว้ในแต่ละใบเพื่อไม่ให้ใบเก่าเปลี่ยนตามเมื่ออัตราเปลี่ยน
- เหตุผลที่ปัดหัก ณ ที่จ่ายตามอัตรา: ตรงกับการออกหนังสือรับรองการหักภาษีที่แยกตามประเภทเงินได้

## DEC-013: วงจรสถานะและเลขที่ PO

- สถานะ: แทนที่ด้วย DEC-015 เมื่อ 2026-11-08
- วันที่: 2026-11-02
- วงจร: `draft → sent → received → closed` และ `cancelled` จาก draft หรือ sent โดยต้องมีเหตุผล การเปลี่ยนสถานะล็อกแถวด้วย `select_for_update` เพื่อกันการกดซ้ำ
- การแก้ไข: แก้ได้เฉพาะ draft ตรวจที่ service ไม่ใช่แค่ซ่อนปุ่ม
- ไม่มีการลบ PO ใบที่ไม่ใช้ให้ยกเลิก เพื่อให้เลขที่ทุกเลขตรวจสอบย้อนหลังได้
- เลขที่: ออกตอนสร้างร่างจากตาราง `PurchaseOrderSequence` แยกตามปี พ.ศ. ของวันที่สร้าง (Asia/Bangkok)

- สถานะ: ยืนยันแล้ว (ตาม requirement ว่า Admin ทำได้ทุกอย่าง)
- วันที่: 2026-11-02

- ข้อควรทำก่อน production: กำหนดวิธีมอบสิทธิ์ให้บทบาทผู้ดูแลระบบนอก DEBUG เพราะ bootstrap ทำงานเฉพาะเครื่องพัฒนา

## DEC-015: PO เป็นทะเบียนตามรายงานระบบเดิม ไม่ใช่ใบสั่งซื้อแบบมีรายการสินค้า

- สถานะ: ยืนยันเบื้องต้น
- วันที่: 2026-11-08
- ที่มา: บริษัทมีระบบ PO เดิมที่มีขั้นอนุมัติและเชื่อม Bplus ส่วนปัญหาหลักคือแก้ข้อมูลแล้วระบุตัวคนแก้ไม่ได้ ผู้ใช้ให้ทำหน้ากรอกตามช่องในรายงาน Excel ของระบบเดิมก่อน
- การตัดสินใจ: PO เก็บเฉพาะหัวเอกสารตามรายงานระบบเดิม ยอดรวมรวม VAT กรอกตรง ไม่มีรายการสินค้า ไม่คำนวณภาษี ระบบไม่ออกเลขที่เอง และนำตาราง `PurchaseOrderLine`, `PurchaseOrderSequence` กับ `calculations.py` ออก
- การแก้ไข: แก้ได้ทุกช่องจนกว่าจะยกเลิก เพราะเป้าหมายคือรู้ว่าใครแก้อะไร ไม่ใช่ห้ามแก้ Audit Event ของการแก้เก็บเฉพาะช่องที่เปลี่ยน (ค่าก่อน/หลัง) และเหตุผลที่ไม่บังคับกรอก หน้า PO แสดงค่าเดิม → ค่าใหม่
- สถานะ: `new` (ใบสั่งซื้อใหม่), `received`, `closed`, `cancelled` และสถานะอนุมัติ `pending`/`approved` เป็นข้อมูลที่บันทึกตามระบบเดิม แก้ชื่อหรือเพิ่มได้ที่ `PurchaseOrderStatus` ที่เดียว
- การย้ายข้อมูล: migration 0002–0004 แยกเป็นโครงสร้าง แปลงข้อมูล และ constraint เพราะ PostgreSQL ไม่ยอมให้แก้ข้อมูลกับแก้ตารางที่มี FK แบบ deferred ใน transaction เดียวกัน
- ทางต่อไป: โครงนี้ตรงกับคอลัมน์รายงาน จึงเพิ่มการนำเข้า Excel ของระบบเดิมเข้าตารางเดียวกันได้ภายหลัง

## DEC-016: นำเข้าผู้ขายจาก Excel ของระบบเดิม และเครดิตแบบไม่ระบุ

- สถานะ: ยืนยันแล้ว
- วันที่: 2026-11-09
- ตัวอ่านไฟล์: `modules/procurement/xlsx_reader.py` อ่าน .xlsx ด้วย standard library (zipfile + ElementTree) แทนการเพิ่ม openpyxl เพราะเครื่องผู้ใช้ build image ใหม่ไม่ผ่านเมื่อเน็ตเข้า Docker Hub ไม่ได้ จำกัดขนาดไฟล์ที่อัปโหลด 15 MB และขนาดเมื่อแตกไฟล์ 60 MB
- ขั้นตอน: อัปโหลด → แสดงตัวอย่าง (เพิ่มใหม่/อัปเดต/ไม่เปลี่ยน พร้อมค่าเดิม → ค่าใหม่) → ยืนยัน ข้อมูลระหว่างรอยืนยันเก็บใน session แล้วคำนวณความต่างใหม่อีกครั้งตอนบันทึก
- กติกา: จับคู่ด้วยรหัสผู้ขาย ไม่มีการลบ ไฟล์เป็นแหล่งข้อมูลหลักของชื่อ รายละเอียด ประเภท กลุ่มเจ้าหนี้ และสถานะใช้งาน ยกเว้นเครดิต: ถ้าไฟล์ไม่ระบุ จะไม่ลบค่าที่ฝ่ายบัญชีกรอกไว้
- Audit: ผู้ขายแต่ละรายมีเหตุการณ์ create/update เหตุผล "นำเข้าจาก Excel" และมีเหตุการณ์สรุปการนำเข้า (`procurement.supplier_import`) บอกชื่อไฟล์และจำนวน
- เครดิต: `Supplier.credit_days` เป็น null ได้ (= ไม่ระบุ) และนับเป็น 0 วันเวลาคำนวณ
- วันครบกำหนดจ่าย: `PurchaseOrder.due_date_manual` บอกว่ากำหนดเองหรือคำนวณ เมื่อเครดิตของผู้ขายเปลี่ยน PO ที่ยังเปิดและไม่ได้กำหนดเองจะคำนวณใหม่ พร้อมบันทึกประวัติในแต่ละใบ

- เหตุผล: Django ผูก migration ไว้กับชื่อ app การย้ายโค้ดไปโฟลเดอร์ของคนจะทำให้ฐานข้อมูลที่มีอยู่ใช้ต่อไม่ได้ ทั้งสองคนยังต้องแก้ไฟล์กลาง (`settings.py`, `urls.py`, `base.html`) อยู่ดี และเมื่อคนเปลี่ยนหน้าที่ ชื่อโฟลเดอร์จะไม่ตรงกับงาน จุดรวมโปรแกรมคือ `manage.py` + `INSTALLED_APPS` + `urls.py` อยู่แล้ว
- ความปลอดภัย: repository ต้องเป็น Private, `.gitignore` กัน `.env` และไฟล์ข้อมูล `.xlsx` `.xls` `.csv`, GitHub Actions รัน `makemigrations --check` และเทสต์ทั้งหมดกับ PostgreSQL 18 ด้วย `DJANGO_DEBUG=false` และ secret ของ CI เอง
- การแบ่ง (สมมติฐาน): double ดูแลโครงระบบ identity และ audit ซึ่งเพื่อนทำไว้, beet ดูแล procurement ซึ่งพัฒนาต่อในรอบนี้ แก้ได้ที่ `CODEOWNERS`
